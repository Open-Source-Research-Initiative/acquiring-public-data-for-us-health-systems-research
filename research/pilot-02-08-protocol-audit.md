17 November 2026. Review by GPT-6.1 agent for the coordinator; based on the public protocol, case records and executor conditions, without inspecting private reference answers or candidate outputs, executing native workflows or requesting health data. This is a prospective consistency review, not independent human review or a finding that any case is ready, has run, or has succeeded. Cole Lyons is the human lead; major scientific claims and progression remain for human review.

## Conditions to resolve and record before each launch

1. The existing [executor conditions](../protocol/pilot/executor-conditions.md) explicitly restrict the first launch to case 01 while the remaining locks are incomplete. The lead's current authorization covers routine completion and cases 02–08; record a dated prospective amendment identifying this authorization, current qualification and the case-specific launch conditions, while preserving the original conditions and case 01 unchanged. Qualification for case 01 alone does not establish every new runtime, mount, host, capture method or command is qualified. The pilot README and case status fields include historical preparation statements; identify them as such rather than silently treating draft packets as locks.
2. Lock the exact selected task, revision, permitted documentation, installed dependency manifest and hashes, actual runtime, mount/caches, network conditions, capture procedure, limits, observation window and executor packet hash before the native invocation. Record unavailable dependencies or unsupported conditions as a terminal barrier; never patch source, change source, narrow a default, or change a selected example to obtain an output. Lock each runtime's actual artifact and identify its corresponding selected case, including failed and blocked setups in the case disposition and eligible selected-system denominator. A missing runtime is not evidence of ineligibility and does not authorize replacement.
3. Preserve the native invocation and arguments below. A wrapper may capture an in-memory object after the native call without changing its source or parameters; freeze that wrapper in advance and distinguish wrapper/capture errors from native errors. Preserve types, missing values, duplicate rows and attributes needed for later comparison (for R, an RDS plus documented metadata is preferable to CSV alone; Python and PHP capture must likewise preserve the returned value and types). Record the capture format, serializer/runtime version, actual files and digests. A printed preview or truncated command log is not the full result. If capture fails, retain the error and classify output availability accordingly; do not silently rerun or reconstruct it.
4. Isolate task-only executor material from private reference material. Hash the independent capture plan before execution, keep reference preparation independent of candidate output, and lock primary output and attempt log before any assessment disclosure. Record timestamps and roles. Reference requests share the original case resource ledger and observation window. Contamination or absent/comparability-limited evidence must remain visible. HTTP proxy mediation means publisher certificate validation is by the proxy; it does not establish the candidate's own TLS verification.
5. Preserve the original attempt, native exit/error, interruption, model and command logs, capture status, elapsed and active time, resource and network accounting and output inventory, including empty and partial results. At most one justified transient retry **or** one later diagnostic repeat is permitted, not both. Record rationale, phase, timing, changed conditions, inputs, outputs and cumulative resources; a diagnostic repeat cannot replace the primary outcome. Avoid calling a wrapper failure a software failure or a denied redirect publisher unavailability.
