## Eligibility and evidence

An eligible lead needs inspectable implemented acquisition code for an external, publicly published, non-patient-level U.S. health-systems or population-health source. Public provider and facility records are in scope; individual survey microdata and patient records are out. A broken, old or inaccessible workflow can remain eligible if implementation and scope are established. Websites, standards, hosted tools without inspectable acquisition code and offline parsers are companion resources. Non-U.S. implementations are recorded as outside scope, not used to fill a quota. No candidate execution, package installation or health-payload collection is part of screening.

Read public official source code, repository metadata, project documentation and publisher documentation. Record actual inspection time, revision and file path or URL; preserve response hash when available, status/errors and material access limits. A README promise alone does not prove implementation. Inspect the call/path that obtains external data and evidence of U.S. and aggregate scope. Record one of `eligible`, `companion`, `excluded`, or `unresolved` with a specific reason. If code or scope cannot be established, retain `unresolved` instead of inferring absence. Separate population eligibility from suitability for the future nonpilot, non-team frame.

The record format is a JSON object with `batch_id`, `issue_url`, `performed_by`, `started_utc`, `finished_utc`, `limitations`, and `records`. Each record has `id`, `title`, `seed_url`, `canonical_system`, `classification`, `reason`, `acquisition_entrypoint`, `us_scope`, `data_level`, `pilot_case`, `team_authored` (`true`, `false`, or `null`), `lineage_notes`, `evidence` (objects with `url`, `accessed_utc`, `observation`, `revision`, `path`, `sha256`, `access_status`; unknown optional values may be null), and `uncertainties`. Do not label externally authored code as independently verified ownership; unknown affiliation remains unknown. Cross-check records refer to seed IDs and retain initial and proposed classifications with evidence and reconciliation reasons.

## Contributor workflow and completion

Choose an open batch issue, comment with the IDs you will check to avoid overlap, and submit a PR or a source-linked comment. Anyone may challenge a model draft or add evidence. No volunteer is assigned without their agreement. Domain issues remain open for corrections while the overall round is being assembled; `model_work_complete` means an automated deliverable is available, not PI acceptance.

Each issue names its inputs, outputs, dependencies and acceptance criteria. A coordinator reconciles cross-checks, preserves dissent, verifies the ledger and prepares a packet only after all assigned model jobs have terminal records: completed, or blocked/unresolved with attempted work, evidence and impact stated. A blocked record is not a completed scientific objective. Failed evidence thresholds remain failed; absence of an oracle is not proof of bad software. Do not require intermediate human approvals for routine screening or model adjudication.

The final packet contains the fixed scope and counts, exact record and review versions, search coverage, access failures, lineage and exclusions, disagreement history, validation, model assistance, major claims, limitations and stop/revise/continue options. Cole supplies one explicit PI decision with its scope, date and artifact version. PI sign-off does not become an independent-human review claim. Main execution, merge and scientific release remain distinct actions and are not authorized by a model's ready status. See `governance/final-pi-review.md` for the review policy.
