The recommendations below are proposed operational decisions, not changes to the locked study method.

## Decisions for the human lead

1. **Release identity and install route.** The protocol ranks a “stable tagged public release” before a “non-prerelease published release,” but most published releases have tags, while a package registry version can diverge from repository tags or default installation. Recommended: define a stable release as a maintainer-designated non-prerelease release with an immutable matching source tag, ordered by release publication timestamp before the cutoff; fall back to a clearly versioned non-prerelease package only if provenance links it to a source revision, then to the default-branch commit. Record package version, source revision and artifact hash separately. A component-specific tag may be the only actual release in a monorepo: retain it when maintainer documentation supports its stability and component identity; otherwise mark stability unresolved. Ambiguous chronology or absent source link stays unresolved. Follow the chosen revision's documented installation route; if that route installs an unpinned newer package, record a revision mismatch and do not silently substitute code. **Tradeoff:** a maintainer's documented current default may be more representative than the latest versioned artifact, but changing the primary rule after observing problems biases results.
2. **Workflow inventory and intended task.** Uniform sampling can overweight a library with many trivial wrappers relative to an integrated pipeline. Recommended: define a workflow as one documented native acquisition entrypoint plus materially distinct upstream source family and output contract; collapse endpoint/parameter variations that only change a filter, date or geography. Preserve all enumerated entries and uncertain grouping decisions, then draw once per system with a recorded seed and stable ordering. The unit estimates a system-weighted, selected documented path, not a probability sample of user behavior or all executions. Use default/example hierarchy for parameters; assess resource barriers without silently choosing an easier workflow. If a function cannot be operationally called from documentation, retain it if eligible and record documentation barrier.
3. **Source families and pilot selection.** Count source families by originating publisher and distinct dataset program with materially different release semantics (e.g., HCRIS and NPPES are separate CMS families; provider utilities sharing the same NPPES release are one), not code libraries, file URLs, or separate years. Maintain a source-to-family table and adjudicate ambiguous multi-source cases before selection. For a workflow requiring multiple sources, retain each dependency and predeclare the primary source relevant to the native task; multi-source cases do not count twice toward the number of cases. The eight-case purposive pilot must cover at least three families; the three output comparisons must involve at least two. Cases researched during proposal preparation may be retained: disclose prior code/doc inspection and selection rationale, freeze the candidate list and decisions before pilot outcomes, and do not treat them as a random or blind sample. No replacement on a failed or blocked attempt. **Tradeoff:** familiar cases make setup faster but can bias task choice and effort estimates, so retain at least some less-familiar cases and report case-specific familiarity.
4. **Proof of acquisition and comparison.** Define the primary endpoint at the selected task boundary: an independently attributable source and release or matched current snapshot, plus a predeclared evidence appropriate to full download or bounded query. A filename, HTTP success, schema or hash alone is insufficient; hash proves equality to captured bytes, not source truth or completeness. Full-release verification needs a defensible release manifest, publisher checksum or independently justified completeness reference; otherwise report bounded verification or unverified. For query cases freeze query, keys and selected fields and compare independent publisher observations in a predeclared window; drift or hidden input means non-comparable or unknown, not failure. Output source-to-output fidelity must compare actual produced values with independently prepared observations; a prepared fixture, schema match or successful exit does not satisfy the three-comparison progression gate. Any contradicted values count as an assessable comparison, not as software success. No claim that source data are correct or fit for a substantive research question follows.
5. **People, time and isolation.** The 80-hour limit means human person-hours, including all supervision, reference prep and independent review; track agent wall time and metered cost separately. Set a timestamped pilot start and record any pre-start selection, reference and setup hours separately so moving work across the boundary cannot disguise total effort. Proposed decision for the lead: whether the 80-hour ceiling covers case-selection and preparation already underway; if excluded, report both the included pilot subtotal and full feasibility effort, with reasons. A single human may continue exploratory search and packet preparation while a second human is unappointed; no independent human-review claim or main progression can occur until the second person actually checks required evidence. A template called sealed is not access control: before any execution, demonstrate the executor cannot read real assessment records and retain the access test, then lock output before unsealing. If a human prepared the references and supervises the same executor, record potential information leakage and keep instructions limited to the execution packet. If access control fails, mark contamination and do not claim separated independent assessment. Neither this recommendation nor a VM qualifies as authorization to execute.

## Residual design limits

Three assessable pilot comparisons across two families are a feasibility threshold, not evidence that a subsequently sampled main frame will have useful references. The candidate and search frame may be small, selective, correlated through common source dependencies and biased by English and discoverability. An observed no-demonstration result combines several barriers under this particular procedure and does not establish intrinsic software failure. Retain original observations, counterexamples, material intervention logs and unresolved outcomes. A second human's availability and actual workload are not established.
