## Workspace-backed scratch

The observed `/workspace` filesystem is ext4 mounted `rw,nosuid,nodev,relatime`, with no displayed project-quota mount option. The unprivileged account can access `/dev/fuse`; `fusermount3` and the libfuse3 runtime are installed, but this inspection found no `bindfs`, `fuse2fs`, `guestmount`, Python FUSE binding, or libfuse3 development headers. A subsequently extracted workspace-local fuse2fs runtime mounted disposable 32 MiB and sparse 100 GiB ext4 images. Synthetic small-image capacity and integrated sandbox probes, plus a 100 GiB mount and 1 MiB write smoke test, passed; see [quota evidence](../../evidence/executor/quota-checks.json). These component checks do not establish the complete executor boundary. No host filesystem settings or persistent mounts were changed.

The tested FUSE filesystem uses a bounded workspace ext4 image; its integration into a complete executor is not yet qualified. It would need to enforce aggregate allocated storage, metadata, and inodes across all writable paths, including concurrent writes, sparse files, hard links, renames, truncation, open-but-unlinked files, mmap, fallocate, and daemon restart/error handling. The daemon and backing store must be inaccessible to the candidate, survive or fail closed on client/daemon termination, and have no writable bypass through other mounts, sockets, inherited file descriptors, shared memory, or host tools. An output collector must use the same accounting boundary. Block-device image size alone is not proof of enforcement: an unprivileged process cannot simply mount a conventional ext4 image without a suitable userspace filesystem implementation. A purpose-built FUSE implementation has a substantial correctness and security burden; an available device and userspace library are insufficient evidence.

Qualify a selected implementation in a disposable workspace directory with a deliberately small limit before allocating a case volume: independently measure backing allocation and writes; exercise parallel writers and the edge cases above; confirm failed writes and fail-closed daemon loss; check all writable locations and escaping descendants; and verify cleanup. Record actual physical footprint, metadata/reserve overhead, any overshoot, and how the 100 GiB protocol limit is interpreted. Tests must not fill the host filesystem. A tmpfs cap would share the system memory budget and is not an equivalent 100 GiB workspace-backed scratch volume. Neither an advisory monitor nor per-process file-size limits establish an aggregate hard quota. The 32 MiB implementation checks passed, but a full 100 GiB fill and complete-runtime accounting were not tested. Retain the overall quota gate as unresolved until every writable route and case resource accounting is verified; do not weaken the limit or claim the pilot qualified on component tests alone.

## HTTPS egress and source authentication

A CONNECT proxy that checks only its requested hostname or resolved IP cannot establish that the encrypted inner TLS request uses the same authority: shared addresses and domain fronting can defeat that policy. IP restrictions, a DNS check, and client proxy environment variables alone do not fix this. Direct networking must also be technically unavailable from the isolated executor, and redirects, DNS, alternate protocols and inherited sockets must stay inside the policy.

A possible stronger design is a dedicated TLS-intercepting proxy with an ephemeral private CA trusted only in the isolated execution environment. For each request it would constrain the CONNECT authority, client TLS server name and HTTP authority to the approved destination and independently validate the upstream TLS certificate and hostname using an unmodified public trust store. It must fail closed on disagreement, unavailable validation, unsupported protocols, tunnel upgrades, or bypass attempts; prevent HTTP/2 connection coalescing and other cross-authority requests from widening policy; and apply the same rules and metering to redirects. DNS resolution and outbound connections remain proxy-controlled, with prohibited local, private and infrastructure addresses denied. A synthetic adversarial test must include a permitted and a forbidden hostname sharing an IP, mismatched SNI/Host, redirect to a forbidden destination, direct network bypass, DNS rebinding, invalid upstream certificate and exhausted transfer budget. Test actual client stacks and concurrent connections, and record precisely what is counted and bounded.

This changes the client's TLS peer: the proxy, rather than the candidate, authenticates the upstream publisher. A generated local CA must never replace or disable the proxy's own upstream certificate verification; source authenticity and the changed transport must be explicitly recorded. Applications with certificate pinning, their own trust stores, unsupported proxy behavior, HTTP-only sources, or incompatible TLS features may fail or require separate treatment. Trust-store and proxy configuration can materially affect the native workflow and must be frozen and disclosed; do not patch candidate code, silently turn off verification, or claim an intercepted run demonstrates the original end-to-end client behavior. Treat an incompatible client or unsafe source as a typed block unless a prospectively reviewed protocol decision specifies otherwise. This is an architecture option, not a demonstrated implementation or a substitute for the pilot's packet lock and review.
