# Pilot executor isolation: decision and evidence

Historical initial probe, 17 November 2026. The later [executor conditions](executor-conditions.md), [current qualification receipt](../../evidence/executor/qualification.json) and [pilot observations](../../evidence/pilot/README.md) supersede its runtime disposition. The following retains the original finding.

Original status: preparation, 17 November 2026. **NOT QUALIFIED for blind execution.** No third-party code, health data, production system, install, privileged operation, or service registration was used. The probe below is a synthetic namespace test, not a security certification. Human reference preparation and primary execution remain separated by procedure only until an enforceable boundary is established; do not characterize that as blinded execution.

## Observed local environment

`bob-admin capabilities` reported only unprivileged capabilities/workspace-status and the documented fixed workspace mount/prepare operations; `bob-admin workspace-status` verified Samsung SSD 990 PRO at `/workspace`. `id` showed builderbob uid/gid 1000. `/workspace` itself is root-owned mode 755, and this repository is builderbob-owned mode 775. `unshare`, `timeout`, `prlimit`, `systemd-run`, `setpriv` and `nsenter` are available; `bwrap`, `podman` and `firejail` were not found on PATH. The Docker client exists, but `docker version` could not connect to `/var/run/docker.sock`. `unshare --user --map-root-user --mount --net --fork true` succeeded. User namespace setting was 1; a transient user systemd scope also started. These observations do not establish a hardened sandbox or a usable VM.

A temporary synthetic canary and empty directory were created inside this repository. In a new user/mount/network namespace, a private bind mount of the empty directory over the canary directory caused the canary read to fail; `/etc/passwd` remained readable in that namespace. The host could still read the canary. Temporary files were automatically removed. Result: **a selected pathname can be hidden inside one process namespace**, not a complete file, process, network or agent isolation test. An initial attempt to create the temporary directory directly under `/workspace` failed with permission denied. No claim is made that the agent's other tools inherit that namespace, that the mount cannot be bypassed through another path, or that malicious code is contained.

## Decision and boundary

A fresh Codex agent operating with ordinary host shell or unrestricted filesystem tools under the same builderbob identity can read reference artifacts directly or through tools, regardless of a child process mount mask. A prompt instructing it not to read references, a same-UID mode bit, a masked pathname, or a fresh conversation does not establish a boundary. Model context, tool results, prompts, terminal output, paths, logs, caches, network endpoints and messages can all leak oracle values. We have not demonstrated a way in this environment to restrict a Codex agent to a single constrained tool while removing all host exec/file access. Therefore **the proposed agent-assisted blinded attempt is blocked pending a separately verified executor boundary**. Do not launch real cases under the current tools and label them independent or blind.

Preferred future design: a separately administered disposable VM or host identity with no access to the reference store, no inherited credentials, only a case packet, a controlled outbound allowlist and an isolated writable scratch disk; a broker exposes only bounded actions and redacted outputs. The reference preparer keeps expected values and comparator outside the VM, evaluates outputs after primary lock, and grants no shell/host filesystem tool to the executor. A genuinely separate identity or VM is necessary but not sufficient: check network, shared mounts, logs, credentials, tool routing and host control. Prove the agent cannot request host-side tools, retrieve references via alternate paths or send unreviewed outputs into its context. The precise mechanism and provider remain unresolved; introducing accounts, VMs or service registrations is a separate scoped administrative decision and not performed here.

An alternative is a deterministic, reviewed runner that executes only a fixed documented command plan in a disposable isolated environment, with no autonomous agent and no reference material. This changes the evaluator regime and must be specified before sampling; it still needs a boundary against arbitrary candidate code, an output oracle held separately, and resource controls. If neither option can be verified, perform a transparent **unblinded feasibility pilot**, disclose the exposure, do not treat it as a blinded independent assessment, and revise the primary method before collecting its results. Any change in regime requires a prospectively approved protocol amendment and an estimate of its effect on the question.

## Preflight and control verification for a future executor

1. Independently provision an isolated, disposable image and scratch volume; record image digest, CPU, memory, network, disk and identity. Prevent host mounts, privileged containers, production access, inherited credentials and agent host-shell tools. Static safety review precedes any candidate run. Ordinary documented dependency installations within the future sandbox require permitted network policy and logged versions; no source patch, provider change or undocumented fix is allowed in primary.
2. Establish and test an external egress allowlist or equivalent policy with both permitted and forbidden synthetic endpoints, DNS and redirect handling; default-deny network is needed where possible. A network namespace alone disconnects networking and is not proof of a controlled functional allowlist. Record if limits cannot be enforced; do not rely on instructions to the agent.
3. Test inaccessible synthetic canaries at all reference locations and via absolute path, symlink, alternate mount, process context, tool invocation, logs and network, including from the agent interface itself. A denial in one shell child is insufficient. Test no host tool is available to the executor, including generic shell, file search, Python, browser, hidden resources and other agents. Do not use actual reference answers for a leak test. Record both attempted routes and observed results, and independently review failures.
4. Enforce elapsed wall time externally with a supervisor (`timeout` is available but has not been tested for descendant/process escape); account for a maximum 4 VM-hours and 16 allocated vCPU-hours on four vCPUs, and 3 active executor hours. A user systemd scope can be started, but CPU, memory, descendant cleanup and disk enforcement were not verified. Measure CPU and VM wall time separately. Test CPU/memory and process-tree cleanup using only synthetic workloads before relying on limits.
5. A 100 GiB local scratch quota and 20 GiB network transfer cap require verified independent controls and counters. No disk quota, per-case byte cap, network metering, egress filter or egress stop was demonstrated. A quota/monitor must stop at the ceiling rather than merely report after it; log overshoot and race behavior. Reference data must not be included in disk/network counters as if downloaded by the evaluated workflow. Until these controls are proved, technical limits are specifications, not demonstrated enforcement.
6. Before each primary attempt freeze and timestamp case selection, documentation, environment, input/release, expected artifact and oracle specification, prompts, model identity, tools, retry and stop rules. The executor receives only the permitted packet; the coordinator supervises actions within the locked procedure without disclosing source-derived reference values. Capture redacted transcript and tool/action ledger, outputs and resource usage. Lock the primary outcome before any bounded repair; a separate assessor checks output against held-out evidence; independent human review is required before claiming it. Logs may themselves carry sensitive or reference information, so access must follow the same separation.

This preparation does not authorize author contact, production access, extra accounts or host/service modification. Routine isolated setup and feasibility attempts fall under the coordinator's delegation once technical prerequisites pass. The present probe does not resolve the executor boundary and does not establish operational readiness.
